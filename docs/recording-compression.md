# Local recording compression (2026-11-05)

Users can select a recording up to 100,000,000 bytes. Files at or below the existing 50,000,000-byte private storage limit keep the previous upload path. Larger originals are converted locally to mono 16 kHz MP3 at 32 kbps before creating a run or contacting storage. The compressed output, not the larger original/video, is archived. The existing server-side 25 MB preparation path remains unchanged.

Mediabunny reads the File as a BlobSource in samples, with its bundled LAME WASM encoder running in a worker. The codec is dynamically imported; no CDN, third-party media transfer, cross-origin isolation change, or Supabase upgrade is required. The original 100 MB file is never posted to the API. Run creation uses the prepared filename and byte length, and storage receives that same prepared file. Local preparation runs before any paid model call.

Output must fit 25,000,000 bytes and its duration must match the complete audio track within one second. Multiple audio tracks are rejected instead of silently dropping speakers. Video is discarded, while stereo channels within one audio track are downmixed to mono. Unsupported decoding, invalid media, excessive output and cancellation return a clear error without creating a run or uploading a partial file. Cancel and unmount free conversion resources. A successful prepared file is cached for upload retries until another source is selected. The screen must stay open for local compression/upload/enqueue; durable server processing continues only after the existing queue acknowledgment.

Validation: node tests compressed a 97,902,044-byte, 37-minute synthetic WAV to 8,880,516 bytes and verified full duration plus audible markers at both ends using FFmpeg. Boundary validation, unchanged small files, cancellation and malformed input passed. Isolated Chromium and WebKit tests converted a valid 50,161,496-byte M4A container to 40,500 bytes (10.01 seconds); no external media requests occurred. Browser fixture is for the Vite development server, not a production entry point. Run npm run test:recording-compression; with Vite running locally, npm run test:recording-compression:browser. Dependencies are from npm; no audit findings were attributed to the newly added media packages. Bundled license notices are in public/licenses/audio-compression.txt.

No real customer recording was used or uploaded in validation, and no OpenAI request was made.
